# План: стабильная совместимость EPUB с PocketBook (80/20, быстрые победы)

## Цель
Сделать так, чтобы EPUB, создаваемые проектом, **не “застревали” на первой/любой странице на PocketBook**, даже если исходная страница содержит `picture/source`, `svg`, “грязные” переносы строк (`<br>`, `<hr>`), виджеты и т.п.

## Почему ломается (зафиксировать как инвариант для работ)
PocketBook часто рендерит EPUB2 как **строгий XHTML/XML**. Браузерные ридеры (включая Beautiful Epub Reader 1.7.9) обычно **терпимы к невалидной разметке** и “чинят на лету”.
Отсюда правило: если наш `chapter*.xhtml` не является корректным XHTML-подмножеством -> риск “залипания” высокий.

## Критерии приемки (проверяемые автоматически)
1) `OEBPS/chapter*.xhtml` парсится как XML (строго), без “mismatched tag”.
2) Нет опасных паттернов, известных по кейсам:
   - `<source ...>` без `/>`
   - `<br>` и `<hr>` без `/>`
   - `<picture>`, `<source>`
   - inline `<svg>` (по умолчанию вырезаем)
3) EPUB-упаковка корректна:
   - `mimetype` - первый entry и stored (без сжатия)
   - `content.opf` содержит все `chapter*.xhtml` и `images/*`, на которые есть ссылки
4) Ручной smoke-test на PocketBook: проблемные файлы листаются (это единственная часть, которую CI не докажет).

## Задачи (t1...): отсортировано по “быстрым победам” и эффективности

### Быстрые победы (самые критичные 80/20)

#### t1. Зафиксировать минимальный “PocketBook-safe XHTML” контракт
- Суть: описать набор запрещенных/обязательных конструкций и почему.
- Результат:
  - короткий документ (например, `docs/decisions/...` или `docs/status.md` + ссылка) с правилами:
    - все пустые теги только `... />`
    - запрет `picture/source`, запрет inline `svg`
    - разрешенный набор тегов (подмножество: `p,h1..h6,ul,ol,li,a,img,pre,code,blockquote,div,span,em,strong,hr,br`)
- Время: <= 1.5ч

#### t2. Добавить “быструю” проверку валидности XHTML в тестах (без привязки к реализации)
- Суть: тест, который берет готовый `chapter1.xhtml` (из fixtures) и проверяет:
  - строгий XML parse (через `xmldom`/`sax`/любой минимальный парсер в Node; либо собственный “строгий” чек паттернов + стандартный XML парсер)
  - отсутствие опасных паттернов regex’ом
- Fixtures:
  - проблемные: `_2__2026-01-30.epub`, `Everyone_should_...epub`, `MCP_Tool_Registry_...epub`
  - контрольный: `sample/_red_mad_robot__2026-01-30.epub`
- Важно: тесты должны ломаться на текущих проблемных EPUB (чтобы доказать, что тест ловит баг).
- Время: <= 2ч

#### t3. Встроить “санитайзер XHTML” в пайплайн генерации EPUB (минимальный фикс)
- Суть: перед упаковкой EPUB прогонять HTML через нормализатор, который:
  1) `picture` -> заменяет на `img` внутри (если нет `img` - удаляет весь `picture`)
  2) удаляет все `<source ...>` (или преобразует в `<source ... />`, но лучше удалить)
  3) приводит `<br>`/`<hr>` к `<br />`/`<hr />`
  4) вырезает inline `<svg>...</svg>`
  5) `figure/figcaption` разворачивает в `div + img + p.caption` (или хотя бы заменяет `figure`->`div`, `figcaption`->`p`)
- Результат: новые EPUB не содержат известных триггеров.
- Время: <= 2ч

#### t4. Регрессионные автотесты “EPUB output contract” (черный ящик)
- Суть: тест генерирует EPUB из заранее сохраненного “грязного” HTML (fixtures HTML) и проверяет контракт на результат:
  - `chapter1.xhtml` проходит t2-проверки
  - ссылки на `images/...` существуют в zip
  - `content.opf` содержит все нужные item’ы
- Важно: тесты не должны зависеть от конкретных внутренних функций (проверяем результат-артефакт).
- Время: <= 2ч

### Среднесрочные улучшения (высокая отдача, но не блокируют)

#### t5. Расширить санитайзер: интерактивные/виджетные узлы -> “плоский текст”
- Суть: для элементов, которые часто приходят из “приложений” (tooltips, quiz-обвязки и т.п.):
  - удалять элементы управления (`label`, `button`, `input`, `svg` уже удаляем)
  - сохранять только текстовое содержимое в `p/span`
- Критерий: контент читаем, не ломает верстку.
- Время: <= 2ч

#### t6. Разбиение контента на несколько глав при превышении порога сложности
- Суть: если `chapter1.xhtml` слишком большой/сложный (по счетчикам тегов/узлов/объему), разбивать на `chapter1.xhtml`, `chapter2.xhtml`, ...
- Авто-критерии (примеры):
  - больше N блоков/картинок/символов
  - наличие “тяжелых” блоков кода
- Добавить тест: при превышении порога создается несколько глав, и `spine`/`manifest` корректны.
- Время: <= 2ч

#### t7. CLI/скрипт “починить существующий epub” для диагностики (dev-tool)
- Суть: команда, которая:
  - распаковывает epub во временную папку
  - прогоняет `chapter*.xhtml` через тот же санитайзер
  - перепаковывает epub, сохраняя правила `mimetype`
  - печатает отчет “что было исправлено” (кол-во удаленных `source/svg`, нормализованных `br/hr`)
- Это ускорит ручную отладку реальных кейсов.
- Время: <= 2ч

### Рефакторинг (чтобы проект было проще поддерживать)

#### t8. Вынести санитайзер в отдельный модуль с чистыми функциями
- Суть: сделать модуль вида:
  - `sanitizeXhtml(htmlString, options) -> { xhtml, report }`
- Требования:
  - нет зависимости от Chrome APIs
  - детерминированный результат
  - `report` нужен для логов и тестов
- Покрыть unit-тестами на “минимальных” строковых примерах (каждый кейс: `picture/source`, `br/hr`, `svg`, `figure/figcaption`).
- Время: <= 2ч

#### t9. Интеграционный рефактор: единая точка “последнего слова” перед zip
- Суть: в генераторе EPUB определить место, где *всегда* выполняются:
  - sanitize
  - проверка контракта (в dev/test режимах)
  - сбор `manifest/spine`
- Цель: чтобы “грязь” не обходила санитайзер через другие ветки кода.
- Время: <= 2ч

## Автотесты: набор, который реально удержит качество (и не привязан к реализации)
1) **Contract tests (черный ящик)**:
   - вход: fixture HTML -> выход: epub zip
   - проверки: XML-parse ok, запретные паттерны отсутствуют, `opf` и файлы совпадают
2) **Regression tests по реальным EPUB**:
   - тест читает проблемные epub (из fixtures) и запускает “repair” -> проверяет, что repaired epub проходит контракт
   - важно: не проверять “точное содержимое текста”, только структурные гарантии
3) **Unit tests санитайзера**:
   - минимальные строки с `picture/source`, `br/hr`, `svg`, `figure/figcaption`
   - ожидаем: удаление/преобразование + отчет

---

## Риски/оговорки (явно)
- Автотесты не могут гарантировать 100% поведение PocketBook, но **строгая XML-валидность + запрет триггеров** закрывает основной класс “залипаний”.
- Если у конкретной модели PocketBook есть отдельные ограничения (например, на PNG/размеры), это будет отдельный слой (проверки размеров/перекодирование картинок).
